## task 1: 임베딩의 단위를 문서로 잡을 때, 내 요구 사항이 여러개이면 어떻게 해결되는가?

일반적인 RAG(Retrieval-Augmented Generation) 시스템에서는 **문서 하나 = 벡터 하나**, **질문 하나 = 벡터 하나**로 간주해서, 유사도를 기준으로 관련 문서를 검색하고, 그걸 기반으로 LLM이 답변을 생성합니다. 하지만 **질문이 여러 요구사항을 담고 있다면** 단일 벡터로 표현하는 데 한계가 있어**그대로 두면 정보 검색(검색 기반 보강)이 충분히 되지 않을 수 있습니다.**

---

### 🔍 문제 요약

* 복합적인 질문 → 하나의 임베딩 벡터 → 관련 문서 검색 → 일부 요구사항 누락 가능성

---

### ✅ 해결 전략

#### 1. **질문을 의미 단위로 쪼개어 각 요구사항을 별도 임베딩**

* 예:

  > "이 시스템에서 사용자 인증 방식과 데이터 암호화 방식이 어떻게 구현되어 있나요?"
  > →

  * "사용자 인증 방식은 어떻게 구현되었나요?"
  * "데이터 암호화 방식은 어떻게 구현되었나요?"

* 각각 별도로 임베딩 → 검색 → 관련 문서 각각 리턴 → 최종적으로 통합해서 응답 생성

#### 2. **다중 쿼리 확장(Multi-query expansion)**

* 한 질문에서 의미적으로 다양한 관점의 질문을 생성 (예: `query rewriter`, `question decomposer` 사용)
* HuggingFace나 LangChain에서 `question splitter` 또는 `HyDE`, `ReACT` 같은 에이전트를 활용 가능

#### 3. **Dense Embedding + Sparse Retrieval 혼합 (Hybrid Search)**

* Dense는 의미 기반 (예: `sentence-transformers`)
* Sparse는 단어 기반 키워드 매칭 (BM25 등)
* 여러 요구사항이 있을 때 키워드 기반 접근이 유리한 경우도 많음

#### 4. **LLM을 이용해 RAG 전처리**

* RAG 앞단에 LLM을 붙여서 사용자의 복합 요구를 파악하고, 이를 기준으로 검색 쿼리를 분해
* 예:

  ```python
  def decompose_question(llm, question):
      return llm(f"다음 질문을 의미 단위로 나누어주세요: {question}")
  ```

---

### 🧠 추가 개념: 임베딩 벡터의 표현 범위 한계

* 하나의 임베딩 벡터는 보통 **질문에서 가장 중심적인 의미**를 잘 표현합니다.
* 하지만 **여러 sub-topic을 동시에 표현**하기는 어렵습니다.
  → 정보 검색에서 일부만 매치되거나, 특정 요구사항이 누락될 수 있음

---

### ✅ 정리

| 전략         | 설명                  | 장점                  |
| ---------- | ------------------- | ------------------- |
| 질문 분해      | 의미 단위로 질문 나누기       | 각 질문에 맞는 문서 정확하게 검색 |
| 다중 쿼리 확장   | 다양한 관점의 질문 생성       | 정보 누락 최소화           |
| 하이브리드 검색   | 의미 + 키워드 검색 혼합      | 복잡한 질문에 더 강함        |
| LLM 기반 전처리 | 질문 의도를 LLM이 해석 후 분해 | RAG의 성능 보완 가능       |

## task2: 여러 개의 문서를 기반으로 하나의 답변을 도출해야 하는 경우
---

### ❗️문제 상황

> **"하나의 문서에 모든 정보가 있는 게 아니라, 여러 문서에 나뉘어서 있는 경우"**
> 예를 들어:

* 문서 A에는 "암호화 방식: AES 사용"
* 문서 B에는 "이 시스템은 의료 데이터를 처리함"
  → 질문: "**의료 데이터를 처리할 때 어떤 암호화 방식을 쓰나요?**"
  → **A와 B를 함께 봐야 답을 낼 수 있음**

---

### ✅ 해결 방법

#### 1. **Chunk 단위 문서화 + Top-k Retrieval**

* 문서 전체를 임베딩하는 대신, **chunk (단락, 문단, 문장)** 단위로 쪼개서 벡터화
  → 더 정밀한 검색 가능
* 질문 임베딩과 가까운 **Top-k** 문서 조각을 **여러 개** 검색
  → A와 B 조각이 같이 검색될 수 있음

```plaintext
[문서 A-1] 암호화: AES-256
[문서 B-3] 본 시스템은 의료 데이터를 다룬다
```

이 조각들을 **함께 LLM에 주면**, 상관관계를 LLM이 유추할 수 있음.

#### 2. **Context Window 내 조각 조합**

* 검색된 Top-k 문서 조각들을 **context window** 안에 다 집어넣음
* 예: OpenAI GPT-4-turbo는 128k 토큰까지 가능 → 수십 개 조각 삽입 가능
* LLM은 이를 바탕으로 문서 간의 뉘앙스나 관계를 추론 가능

#### 3. **Re-ranking (다시 순위 매기기)**

* Top-20 조각을 먼저 검색하고, LLM 또는 reranker 모델이
  **"이 중 어떤 조각들이 함께 있어야 의미가 맞는가"** 판단해서 재정렬

예시:

```text
Initial Retrieval → 조각 A1, B3, C5, D2
Reranker → A1와 B3는 같이 들어가야 함
→ 최종 Input = A1 + B3
```

#### 4. **Graph RAG / Knowledge Graph 기반 확장**

* 각 문서를 벡터로만 보지 않고, 엔티티와 관계를 추출해서 그래프로 구성
* LLM은 이 그래프를 따라 정보 연결 가능
  → "암호화 방식 ↔ 시스템 ↔ 의료 데이터" 관계 연결

---

### 💡 요약

| 문제             | 해결책              | 설명                    |
| -------------- | ---------------- | --------------------- |
| 정보가 여러 문서에 흩어짐 | Chunking + Top-k | 문서를 작은 단위로 나누고 다수 검색  |
| 관계 추론 필요       | LLM + 긴 context  | LLM이 여러 조각을 조합해서 추론   |
| 중요한 조각 선별      | Reranking        | LLM 또는 별도 모델이 중요도 재평가 |
| 구조적 관계 필요      | Graph RAG        | 관계 기반 추론 가능           |

---

### 🧠 참고로

* LangChain에서는 `Contextual Compression Retriever`, `MultiVectorRetriever` 등이 이런 구조 지원
* OpenAI API 사용할 경우에도 `top_k + reranking + 조합` 조치 가능
* 기초 벡터 DB에서도 `metadata filtering`을 활용해서 조건별 조각 조합 가능
